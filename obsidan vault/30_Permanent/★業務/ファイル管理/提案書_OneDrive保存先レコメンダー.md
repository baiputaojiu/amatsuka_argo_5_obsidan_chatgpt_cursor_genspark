## 1. 背景・課題

業務ファイルは OneDrive（`OneDrive - Example Organization`）上で、年度フォルダおよびテーマ別サブフォルダに整理している。

現行の主な整理軸（例：`010_FY_PREVIOUS`）:

- `（Input）…` … インプット資料
- `（Main）…` … 主管テーマ（スリッター要素開発、自動外観検査 など）
- `（Output）…` … 週報・月報・検討会など成果物
- `（雑用）…` / `（Sub）…` / `（Not in charge）…` など役割別

一方で、次のような課題がある。

- ルート直下や Downloads にファイルが滞留しやすい
- 保存先をその都度思い出す／探すコストが高い
- 「既存フォルダに寄せるべきか／新規テーマフォルダを切るべきか」の判断が都度発生しやすい
- フォルダ一覧は既に `tree /f` で取得・Vault 化しているが、**振り分け判断自体は人手**のまま

---

## 2. やりたいこと（プロダクト定義）

### 2.1 一言

ファイル（および任意のメール文脈）を渡すと、**OneDrive 業務ツリー上の適切な保存先候補を提案**し、必要なら**新フォルダ作成の指示まで含めた手順書を出す**デスクトップ向けアシスタントを作る。

### 2.2 する／しない

| すること | しないこと（初期方針） |
|---|---|
| 保存先の**提案**（既存パス） | ファイルの**自動移動・自動保存** |
| 新規フォルダが妥当な場合の**作成指示**（親パス・提案名・手順） | Google Calendar / GCP 等との連携 |
| 提案理由・信頼度・代替候補の提示 | 人の確認なしでの確定 |
| 人が確定した結果の監査ログ（任意で再学習の種） | 初期からの完全自動運用 |

→ **同期・自動振り分けツールではなく、プレビュー前提のレコメンダー**。

---

## 3. ゴールと成功指標

### 3.1 ゴール

- 保存先判断の摩擦を減らす
- 「ほぼそのまま保存できる」提案を日常運用で使える水準にする
- 誤提案でも、理由が分かり・人が短時間で修正できる

### 3.2 成功指標（案）

- 「提案をそのまま採用」できた割合（例: 週次サンプルで 7/10 以上）
- ルート直下・未整理の滞留件数が減る
- 1件あたりの判断時間（探す＋決める）が短縮される

※ 正解率100%は目指さない。**提案 → 確認のコスト削減**を主目標とする。

---

## 4. 対象データ・入力

### 4.1 振り分け対象ルート

- `C:\Users\example\OneDrive - Example Organization`
- 特に年度フォルダ（`ARCHIVE_01`〜`ARCHIVE_07` 等）と、現行年度の 分類A / 分類B / 分類C 体系

### 4.2 入力形態（想定）

1. ローカルファイル単体、または複数（D&D 等）
2. フォルダ一式のパス受け渡し
3. （任意）Outlook 由来の文脈：件名・差出人・日付・本文抜粋＋添付

### 4.3 判定に使う材料（合意済み）

| 材料 | 用途 |
|---|---|
| ファイル本文（Office / PDF 等のテキスト抜粋） | 主題・テーマ推定 |
| メールメタ（件名・差出人・日付など） | 文脈・主管・関連プロジェクト推定 |
| 人の最終確認 | 採用／修正／新規フォルダ確定 |

ファイル名・拡張子のみのルールは補助とし、語義判断をキーワードだけに強引に落とさない。

---

## 5. 出力仕様

1件（または1バッチ）あたり、少なくとも次を返す。

1. **推奨保存先**
   - 既存フォルダのフルパス、または
   - **新規フォルダ案**（親パス ＋ 提案フォルダ名）
2. **信頼度**（高 / 中 / 低）
3. **理由**（どの材料からそう判断したか）
4. **代替候補**（2件程度）
5. **実行手順（指示書）**
   - 既存: どのパスへ配置するか
   - 新規: どの親の下に何という名で作成し、その後どこへ置くか
   - 任意: コピー用の `mkdir` / `Move-Item` 等スニペット（**実行はユーザー任意**）

ソフトはフォルダの実作成やファイル移動を初期は行わない。人が指示どおり実行する。

---

## 6. 判定の考え方（二段ルーティング）

フルパスを一発当てるのではなく、次の二段が安定しやすい。

### 段1：軸の決定

- 年度（デフォルトは現行年度）
- 大分類（分類A / 分類B / 分類C / その他 / 分類D / 分類E 等）

### 段2：テーマフォルダ

- 既存サブフォルダへ寄せる（例: `（Main）自動外観検査`）
- 適切な既存が無ければ、命名規則に沿った**新規テーマフォルダ**を提案

### ロジック分担（案）

| 層 | 役割 |
|---|---|
| ルール | 再現性の高い軽判定（例: 「週報」→ Output 寄り） |
| カタログ照合 | 既存フォルダ名との部分一致・類似度 |
| AI（語義） | 本文・メール文脈からの主題・大分類推定 |
| 人 | 最終確定（必須） |

---

## 7. システム構想（参考アーキテクチャの借り方）

既存の Outlook→Google 同期ツールは、次のようなレイヤになっている。

- GUI → Services / Engine → Connectors → Models
- Preview（実行前確認）と Audit（履歴）を重視

今回は GCP 連携はせず、同思想だけ借りる。

```
入力コネクタ（ローカルファイル / 任意で Outlook メタ）
  → FileItem 正規化
  → 特徴抽出（名前・本文抜粋・メールメタ）
  → 宛先カタログ（OneDrive 階層 + 役割メモ）
  → RoutingEngine（候補スコアリング）
  → Proposal Preview（人が確定・修正）
  → 指示書 Emit
  → Audit（採用/却下/修正先）
```

自動書き込みが無いため、「同期エンジン」ではなく **Propose → Confirm → Emit instructions**。

### 宛先カタログの初期ソース

- 既取得のフォルダ階層（Vault: `private/local-structure.txt` 等）
- [[private-file-management]] および各 `private-detail-*` の役割メモ（今後充実させる）

---

## 8. MVP（最初の縦スライス）

### 含む

1. 宛先カタログの読込（フォルダ階層＋簡易役割メモ）
2. ローカルファイル入力（単体〜複数）
3. 特徴抽出：ファイル名＋ Office/PDF テキスト抜粋（失敗時は名前のみ・低信頼）
4. メールメタ：初期は手動貼り付け → 後続で Outlook COM 等を検討
5. GUI またはテキストでの候補表示＋指示書（Markdown / テキスト）
6. 採用結果の簡易監査ログ（JSON 等）

### 含めない（初期）

- 自動移動・新フォルダの実自動作成
- 全文を常時クラウド学習
- Teams / Copilot 保存フォルダの自動巡回整理
- GCP / Google 連携

---

## 9. 未決事項（深掘りポイント）

構想を ChatGPT 等で詰めるときの論点。

1. **新フォルダ命名規則**  
   例: `YYYYMMDD_テーマ` か、`（Main）テーマ\サブ` のどちらを標準にするか
2. **既存寄せ vs 新規作成の閾値**  
   類似フォルダがあるとき新規を出さない／信頼度中以下だけ新規可、など
3. **機密・AI利用方針**  
   社内文書本文を外部 AI に渡すか、社内 API / ローカル推論か、抜粋長さ上限
4. **UI形態**  
   tkinter 系 GUI（既存同期ツールと同系統）か、CLI＋指示書中心か
5. **バッチ単位**  
   1ファイルずつ vs フォルダ一式をまとめて提案
6. **現行年度の切替ルール**  
   年度フォルダ切替時のデフォルト更新方法

---

## 10. 非機能・制約（案）

- Windows / OneDrive 業務PC上で動作
- ユーザー向け文言・操作手順は日本語
- 生の業務ファイル名・本文は、可能なら git や共有リポジトリに不用意にコミットしない
- 提案ミスは許容するが、**黙って別場所へ動かさない**（不可逆操作を避ける）
- 監査ログはローカルランタイムディレクトリに保持（既存同期ツールと同様の考え方）

## 12. まとめ

本プロダクトは、OneDrive 業務ツリーへの保存を自動化するのではなく、

**内容・メール文脈・既存階層を踏まえて「置く場所／切るフォルダ」を提案し、人が確定したあとに実行可能な指示を出す**

ことを目的とする。既存の Outlook 同期ツールからは、コネクタ分離・正規化モデル・プレビュー・監査の設計思想のみを参考にし、クラウド予定同期とは独立したプログラムとして進める。
