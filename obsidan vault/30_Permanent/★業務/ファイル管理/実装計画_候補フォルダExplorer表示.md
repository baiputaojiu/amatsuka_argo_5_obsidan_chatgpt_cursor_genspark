# 実装計画：候補フォルダのExplorer表示

## 1. 文書情報

- 対象：OneDrive業務フォルダ向け「保存先レコメンダー」
- 位置付け：MVP 0運用開始後の小改修案
- 作成日：2026-08-02
- 基準ブランチ：`ferch1_保存先レコメンダー修正`
- 基準コミット：`9571858`
- 状態：実装前・レビュー待ち

この文書は実装方法の合意を得るための計画書であり、プログラム本体の変更完了を示すものではない。

## 2. 目的

候補一覧に表示された保存先フォルダを、保存先として確定する前にExplorerで開き、フォルダの中身や位置を確認できるようにする。

この変更で短縮したい作業は次のとおり。

1. 候補の絶対パスをコピーする
2. Explorerへ切り替える
3. アドレス欄へ貼り付ける
4. 対象フォルダを開いて内容を確認する

変更後は、候補一覧からの明示的な操作だけで同じ確認を行えるようにする。

---

## 3. 対象範囲

### 3.1 今回実装するもの

- 候補行のダブルクリックで、その候補フォルダをExplorerに表示する
- 候補選択後のEnterキーでも同じ操作を行えるようにする
- Explorer表示の成功・失敗を既存の画面下部の状態欄へ表示する
- 候補パスが存在しない場合は、フォルダ構成の更新を案内する
- Explorer起動処理を自動テストで差し替えられる構造にする

### 3.2 今回実装しないもの

- OutlookメールのD&D入力
- ローカルファイルのD&D入力
- Explorerから本アプリへのD&D
- フォルダやファイルの自動作成・保存・移動・削除
- 候補を開いたことのAudit記録
- 候補を開いた時点での保存先確定
- Explorer上でのファイル選択や保存操作の自動化
- Explorerウィンドウの位置・サイズ・タブ・再利用方法の制御
- 設定項目、設定画面、外部依存の追加

## 4. 操作仕様

### 4.1 推奨操作

暫定的に次を採用し、レビュー後に確定する。

| 操作 | 挙動 |
|---|---|
| 候補行をシングルクリック | 候補を選択するだけ |
| 候補行をダブルクリック | 候補フォルダをExplorerで開く |
| 候補を選択してEnter | 候補フォルダをExplorerで開く |
| 「選択パスを確定・コピー」 | 従来どおりコピー、確定、Audit記録を行う |

シングルクリックで直ちにExplorerを開く方式は、候補を見比べるだけで複数回Explorerが開くおそれがあるため、初期案では採用しない。

### 4.2 表示対象

- 候補フォルダそのものを開き、その配下の内容を表示する
- 親フォルダを開いて候補フォルダを選択状態にする方式は採用しない
- Explorerが新規ウィンドウ、既存ウィンドウ、新規タブのどれを使うかはWindowsの設定に従う
- 本アプリが保証するのは、指定した候補フォルダがExplorerに表示されることまでとする

### 4.3 画面案内

候補一覧の近くに、次の短い案内を追加する。

> 候補をダブルクリックするとExplorerで確認できます。開くだけでは保存先は確定されません。

Explorer表示成功時の状態欄：

> 候補フォルダをExplorerで開きました。保存先はまだ確定していません。

候補パスが存在しない場合：

> 候補フォルダが見つかりません。フォルダ構成を更新してください。

Windows側の起動処理に失敗した場合：

> 候補フォルダをExplorerで開けませんでした。パスを確認して再度お試しください。

## 5. Previewと確定の分離

Explorerで候補を開く操作は、保存先決定前のPreviewとして扱う。

候補をExplorerで開いても、次は変更しない。

- `audit.jsonl`
- クリップボード
- 確定パス表示
- 現在の検索語
- 現在の入力ファイル
- 候補一覧と選択中の候補
- 自動検索語だけで候補0件だったかの測定値

保存先の確定は、従来どおり「選択パスを確定・コピー」「保存先未定」「却下」のいずれかを人が明示的に押した場合だけ行う。

## 6. 実装方式

### 6.1 Explorer起動処理

Windows標準の`os.startfile()`を使用して、候補フォルダを開く。

- シェル用のコマンド文字列を組み立てない
- 日本語、空白、括弧を含むパスをそのまま渡す
- 起動前に`Path.is_dir()`で存在を確認する
- `FileNotFoundError`、`OSError`をGUI側で捕捉し、アプリを終了させない

Explorer起動処理は小さな関数へ分離し、テスト時に偽物の起動関数を渡せるようにする。これにより、自動テスト中に実際のExplorerを開かない。

想定する責務は次の範囲に限定する。

```text
open_folder_in_explorer(path, launcher=None)
  1. pathが既存フォルダか確認
  2. 既存でなければ例外
  3. launcher未指定時だけos.startfileを使用
  4. 指定された絶対パスを1回だけlauncherへ渡す
```

新しい設定項目や実行時依存は追加しない。

### 6.2 GUIイベント

既存の`ttk.Treeview`へ次を登録する。

- `<Double-1>`：クリック位置にある候補行を特定して開く
- `<Return>`：現在選択されている候補を開く

ダブルクリック時は`Treeview.identify_row(event.y)`を使い、見出し、スクロールバー、空白部分の操作を候補行として扱わない。

候補パスは画面の文字列を再解析せず、現在の`RecommenderSession.candidates`にある`Candidate.absolute_path`から取得する。

### 6.3 既存機能への影響

変更しないもの：

- 候補の生成・折りたたみ・並び替え
- ファイル選択とMSG解析
- Codex相談用プロンプト
- 候補確定、保存先未定、却下
- Auditの9項目
- カタログ更新
- 年度切替

Explorer表示はGUIからWindowsへ候補パスを渡すだけとし、判定コア、Audit、カタログには依存させない。

## 8. エラー時の扱い

### 8.1 候補未選択

- Enterキーの場合は何もしない
- 警告ダイアログを連続表示しない
- 既存の状態を変更しない

### 8.2 見出し・空白部分のダブルクリック

- 何もしない
- 現在の候補選択を維持する

### 8.3 候補フォルダが存在しない

- Explorerを起動しない
- フォルダ構成の更新を案内する
- カタログは自動更新しない
- Auditへ記録しない

### 8.4 Windows側の起動失敗

- アプリを終了しない
- 汎用的な再試行案内を表示する
- OS由来の詳細なパスや例外を新しいログへ保存しない

## 9. テスト計画

### 9.1 単体テスト

1. 既存フォルダの絶対パスを起動関数へ1回だけ渡す
2. 日本語・空白・括弧を含むパスを変更せず渡す
3. 存在しないフォルダでは起動関数を呼ばない
4. 起動関数の`OSError`を呼び出し側が扱える形で返す
5. テスト中に実際のExplorerを起動しない

### 9.2 GUI結合テスト

1. 候補行のダブルクリック相当で正しい候補パスを開く
2. Enterキーで現在選択中の候補パスを開く
3. 見出し・空白部分では起動処理を呼ばない
4. 存在しない候補でもアプリが終了しない
5. Explorer起動失敗後も検索と候補選択を続けられる
6. Explorer表示の前後でAuditの行数が変わらない
7. クリップボード書き込み関数を呼ばない
8. 確定パス表示を変更しない

### 9.3 回帰テスト

- 既存の単体テスト87件を維持する
- 既存のWindows結合テスト3件を維持する
- Ruffのformat checkとlintを通す
- Linux等のWindows外環境でも、Explorerを実起動しない単体テストが実行できる構造を維持する

### 9.4 手動確認

1. ファイル未投入の手動検索で候補を表示する
2. 候補をダブルクリックする
3. 対象候補フォルダの内容がExplorerに表示されることを確認する
4. Enterキーでも同じ確認を行う
5. 確定パス欄が変化していないことを確認する
6. 本番Auditの行数が増えていないことを確認する
7. 「選択パスを確定・コピー」は従来どおり動くことを確認する
8. OneDrive上のファイル・フォルダが変更されていないことを確認する

## 10. 受け入れ条件

1. 候補行のダブルクリックで、その候補フォルダをExplorerに表示できる
2. 選択中の候補をEnterキーでExplorerに表示できる
3. シングルクリックだけではExplorerを開かない
4. 見出し・空白部分の操作ではExplorerを開かない
5. 存在しない候補では、フォルダ構成の更新を案内できる
6. Explorer起動に失敗しても、アプリを終了せず利用を継続できる
7. Explorer表示だけでは、Audit、クリップボード、確定パスを変更しない
8. 候補判定、確定、保存先未定、却下、Codex相談の既存挙動が変わらない
9. 新しい外部依存・設定・ログファイルを追加しない
10. 実行前後でOneDrive上のファイル・フォルダにプログラム起因の変更がない

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| 候補を見比べるだけでExplorerが何度も開く | シングルクリックでは開かず、ダブルクリックを採用する |
| カタログ更新後にフォルダが削除されている | 起動直前に存在確認し、カタログ更新を案内する |
| Explorerの起動に失敗してアプリも停止する | `OSError`を捕捉し、現在の入力状態を維持する |
| 開いただけで確定したと誤解する | 画面案内と状態欄で「未確定」と明示する |
| PreviewがAuditやクリップボードへ副作用を持つ | 確定処理を呼ばない構造と自動テストで固定する |
| Windows外のテスト環境で`os.startfile`を利用できない | 起動関数を注入し、実起動しないヘッドレステストにする |
| OneDrive同期による更新とアプリの変更を混同する | プログラムの書き込み経路を設けず、制御した直前・直後比較を行う |

## 13. レビューで確認してほしい点

1. シングルクリックではなく、ダブルクリック＋Enterを採用する判断は妥当か
2. 親フォルダで候補を選択表示するのではなく、候補フォルダそのものを開く仕様でよいか
3. Explorer起動処理を`explorer.py`へ分離することは、テスト容易性に対して過剰ではないか
4. Previewと確定・Auditの分離に漏れがないか
5. エラー時にカタログを自動更新しない方針でよいか
6. 追加・削除できるテストや記録項目がないか
7. さらに実装負荷を下げられる点がないか
