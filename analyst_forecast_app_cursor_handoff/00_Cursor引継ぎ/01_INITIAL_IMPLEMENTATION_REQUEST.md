# Cursor用・初回実装依頼文

## 目的

Cursorに資料一式を読ませ、仕様の再解釈だけで終わらせず、技術検証と縦断MVPの実装を開始させるための依頼文です。

## 推奨環境

- CursorのAgentモード。
- 利用可能な中で、複数ファイル実装・長文仕様理解・高い推論能力を持つ高性能モデル。
- モデルのAuto切替は避け、作業中はモデルを固定する。

## コピペ用依頼文

```text
このリポジトリにある資料を正本として、「アナリスト予想検証アプリ」の実装を開始してください。

最初に、必ず以下を順番に読んでください。
1. 00_Cursor引継ぎ/00_START_HERE.md
2. 00_Cursor引継ぎ/02_SPEC_AUTHORITY.md
3. docs/05_計画/PRODUCT_VISION.md
4. docs/05_計画/DECISION_LOG.md
5. docs/03_仕様書/METHODOLOGY.md
6. docs/03_仕様書/DATA_MODEL.md
7. docs/03_仕様書/SYSTEM_SPECIFICATION.md
8. docs/03_仕様書/FOLDER_STRUCTURE.md
9. docs/03_仕様書/WORKFLOW_DIAGRAMS.md
10. docs/05_計画/MVP_PLAN.md
11. docs/04_参考資料/PYTHON_TASK_CATALOG.md
12. docs/04_参考資料/PROMPT_CATALOG.md
13. docs/05_計画/OPEN_QUESTIONS.md
14. 00_Cursor引継ぎ/04_IMPLEMENTATION_ACCEPTANCE_CHECKLIST.md

reference/chat_history.md が存在する場合、それは背景確認専用です。正式仕様との矛盾時は正式仕様を優先し、会話中の古い案や撤回済み案を復活させないでください。

このアプリはWindows 11上で個人利用する、日本語のローカルCLIアプリです。自動売買や外部公開は行いません。意味判断は高性能AIに依頼し、ID、フォルダ、ハッシュ、Schema検証、市場データ取得、評価計算、集計、状態管理はPythonで再現可能に処理します。原文は変更禁止です。

今回の到達目標は、docs/05_計画/MVP_PLAN.md の「第0段階：技術検証」と「第1段階：縦断MVP」です。いきなり全媒体収集、全プロンプト、複数アナリスト比較、総合スコア、対話型ダッシュボードまで作らないでください。

実装前に次を行ってください。
A. 現在のリポジトリ構成、Git差分、利用可能な開発環境を確認する。
B. 仕様間の明白な矛盾と、実装を完全に止める未決事項だけを列挙する。
C. docs/05_計画/OPEN_QUESTIONS.md の項目を、blocking / configurable_default / later に分類する。
D. 実装計画を docs/06_実装/IMPLEMENTATION_PLAN.md に作成する。各工程へ対象要件ID、作成ファイル、テスト、完了条件を記載する。
E. 暫定判断を docs/06_実装/IMPLEMENTATION_ASSUMPTIONS.md に記録する。正式な決定を装わないこと。

上記を行った後、重大なブロッカーがなければ質問だけで停止せず、そのまま実装を進めてください。Obsidian Vaultの実パスや最初のアナリスト名が未指定でも、設定ファイルと一時ディレクトリ、匿名の固定fixtureを使用して実装・テストを進められる設計にしてください。ユーザー固有値をコードへハードコードしないでください。

技術構成は、原則としてPython 3.12系、Typer、Rich、SQLite、SQLAlchemy、Alembic、Pydantic、pytestを使用してください。表処理・グラフ・市場データ依存は、必要になった段階で追加してください。採用バージョンは実際の互換性を確認して固定し、理由を記録してください。APIキーや個人パスは .env やローカル設定へ分離し、Gitへ入れないでください。

最初に実装する縦断経路は以下です。
1. CLI起動と日本語ヘルプ。
2. 設定読込みと初期化。
3. 分析対象者ID・案件IDの発行。
4. 案件フォルダ、request.yaml、状態ファイルの生成。
5. raw原文の追記専用取込み、SHA-256ハッシュ、重複検出。
6. 最小の固定JSON SchemaとPydanticモデル。
7. AI出力JSONのSchema、ID参照、原文引用存在の検証。
8. SQLiteへのトランザクション取込みと再実行耐性。
9. 既知の銘柄またはfixture市場データによる最小の方向評価。
10. status.yaml、WORKFLOW_STATE.json、NEXT_ACTIONS.md、OPEN_ISSUES.md の生成。
11. ターミナルへ「次に何をするか、理由、担当、入力、出力、代替案」を表示。

ネットワークや無料データ取得の不安定さでテストが失敗しないよう、unit testはローカルfixtureまたはモックを使ってください。yfinance、FRED、CSVはprovider interfaceの背後へ置き、実ネットワーク確認は明示的なintegration testに分けてください。取得不能な市場値を推測して埋めないでください。

アーキテクチャでは少なくとも次を分離してください。
- domain：予想、情報源、対象、評価状態等の中核モデル。
- application：案件作成、取込み、評価、次行動判定のユースケース。
- infrastructure：SQLite、ファイル、yfinance、FRED、CSV。
- cli：TyperコマンドとRich表示。
- schemas：AI入出力Schema。
- tests：unit、integration、fixture。

ただし、過度な抽象化や将来機能の先回り実装は避けてください。現在の受入条件を満たす最小構成を優先します。

以下は変更禁止の重要方針です。
- raw原文は上書きしない。
- 同一原文はハッシュで識別し、再処理しない。
- AIの意味判断をPythonの曖昧なルールへ置き換えない。
- AI出力は必ずPythonで検証してから取り込む。
- 同じ予想の後日の再表明は別の予想表明として評価し、同時に予想グループで関連付ける。
- 現在予想の投票では同じ人物を再表明回数分だけ水増ししない。
- テーマや業種の代理指標は市場結果を見る前に固定する。
- 発言日時より後の情報を予測対象解決へ逆流させない。
- 過去実績用と現在予想用に収集期間を分けない。同一予想データを評価基準日時点の状態で分類する。
- 総合点一つだけでアナリストを断定しない。
- ループエンジニアリングは初期MVPへ導入しない。

各実装単位で次を行ってください。
- 関連する要件IDまたはタスクIDを示す。
- 先に失敗するテストまたは受入テストを定義し、実装後に実行する。
- formatter、lint、型検査、pytestを可能な範囲で実行する。
- 実行結果と未解決事項を docs/06_実装/IMPLEMENTATION_STATUS.md に更新する。
- 仕様変更が必要なら勝手に書き換えず、変更案、理由、影響範囲を提案する。
- 既存のユーザー変更や無関係なファイルを破壊しない。

最初の作業終了時には、次を報告してください。
1. 実装した機能。
2. 作成・変更した主要ファイル。
3. 実行した検査と結果。
4. まだ未実装のMVP項目。
5. 暫定判断と、ユーザー確認が本当に必要な事項。
6. 次に行う一つの推奨作業と代替案。

計画書を作っただけで終了せず、重大なブロッカーがない限り、実装・テスト・状態更新まで進めてください。
```

## 初回依頼後に確認する点

Cursorの最初の応答で、次が明示されているか確認します。

- 全機能一括実装ではなく、縦断MVPを選んでいる。
- 会話全文より正式仕様を優先している。
- 未決事項をブロッカーと設定値へ分けている。
- 原文不変とAI出力検証を理解している。
- ネットワーク不要のテストfixtureを用意する。
- 次行動案内を後回しにしていない。
